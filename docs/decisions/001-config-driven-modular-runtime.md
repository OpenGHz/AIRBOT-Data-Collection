# ADR-001：配置驱动的模块化 Python + MCAP 架构

## Status

Accepted

## Context

AIRDC 需要同时支持以下现实约束：

- 不同机器人、相机、示教器和观测组合
- 真机手动采集与仿真/自动采集两种运行模式
- 不同数据格式需求，包括 MCAP、ROS 结构化消息和 LeRobot 数据集
- 尽量少改主程序，通过配置完成系统装配

如果把这些能力都写进一组固定脚本，会很快出现以下问题：

- 机器人适配逻辑耦合在一起，难以复用
- 新硬件或新数据格式引入成本高
- 用户需要直接改 Python 代码，而不是替换配置
- 数据格式和元信息不统一，后续可视化、检查和训练接入困难

## Decision

AIRDC 采用以下组合式架构作为当前默认技术路线：

1. 使用 Python 作为主实现语言。
2. 使用 Pydantic + Hydra 风格的配置装配运行时对象。
3. 使用 FSM 管理采集流程状态，而不是把流程控制散落到各个设备适配器里。
4. 将系统拆分为 demonstrator、sampler、visualizer、manager 四类核心模块。
5. 将 MCAP 作为默认的通用 episode 落盘格式，并在保存时同时写入 metadata、attachment 和 topic statistics。
6. 将 AIRBOT 相关默认实现和配置放在 `airbot_ie/`，与通用框架 `airdc/` 分层。

## Consequences

### Positive

- 新模块通常可以通过“实现类 + 新增配置”接入，而不必修改主循环。
- 真机、仿真、自动化、不同示教器之间可以复用同一套主流程。
- MCAP 成为统一默认落盘格式后，检查、可视化、上传和数据转换路径更清晰。
- 通过把 AIRBOT 集成逻辑放到 `airbot_ie/`，核心框架更容易演化为通用层。

### Negative

- 配置层次较深，初学者理解成本偏高。
- Hydra/Pydantic/FSM 的组合让调试路径比单脚本更复杂。
- 多模块可插拔虽然灵活，但也意味着兼容性需要更多测试约束。
- `auto-atomic-operation`、AIRBOT SDK、相机驱动等外部依赖仍然会影响整体可移植性。

## Alternatives Considered

### 1. 单体脚本式采集程序

- 优点：上手快，路径短。
- 缺点：不适合多机器人、多配置、多数据格式长期演进。

### 2. 纯 ROS bag / ROS node-first 架构

- 优点：ROS 生态成熟。
- 缺点：会限制一部分非 ROS 环境，并弱化当前 AIRDC 在 Python 层快速组合与扩展的优势。

### 3. 仅使用 YAML 配置，不保留显式的 Pydantic 模型

- 优点：表面上更轻。
- 缺点：类型约束、默认值管理和运行时校验能力会下降，复杂配置更难维护。

### 4. 直接以内置目录结构输出原始视频和数值文件

- 优点：肉眼可读，容易手动检查。
- 缺点：多模态对齐、元信息保存、工具链兼容性都不如 MCAP 统一容器方案。
